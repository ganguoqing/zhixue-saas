## 1. 产品愿景与核心原则

### 1.1 产品愿景

「智学」不是单纯的 AI 阅卷工具，也不是传统的学生成绩管理系统。

它的核心目标是建立一个完整的教学改进闭环：

**采集学习数据 → 识别知识问题 → 生成教学建议 → 教师实施干预 → 追踪后续表现 → 验证教学效果。**

产品遵循已经确定的设计理念：

> AI 负责发现问题，老师决定行动；每一次教学都会留下记录，并在后续学习中验证效果。

### 1.2 核心产品原则

| 编号 | 原则 | 要求 |
|---|---|---|
| P-01 | 教师主导 | AI 提供建议，不代替教师作出最终教学决定 |
| P-02 | 数据有据可查 | 每项诊断和建议都应能追溯到学习证据 |
| P-03 | 成绩可靠 | AI 建议评分必须经过规定的复核和确认流程 |
| P-04 | 租户严格隔离 | 不同学校之间的数据不能相互访问 |
| P-05 | 教学闭环 | 教学干预需要记录并支持后续效果验证 |
| P-06 | 学科可扩展 | 首期数学，架构支持后续增加其他学科 |
| P-07 | 人工可纠正 | AI 识别、评分、知识点映射均应支持人工修正 |
| P-08 | 历史可追溯 | 关键成绩、评分规则、AI 结果及人工修改应保留版本和审计信息 |

### 1.3 产品范围与优先级

产品面向学校和规模化教培机构，先验证一所学校的教学业务，架构预留独立教师使用能力。覆盖学段为小学三年级至初中三年级；规划学科包括语文、数学、英语、物理、化学、生物、地理、历史、政治，第一阶段仅实现数学。

通用 SaaS 基础平台、通用教学业务与学科专属能力分层设计。学科、知识节点及业务接口不得将数学概念硬编码成通用模型。

P0 表示第一阶段必须交付的核心能力，按 M0-M7 分阶段完成；P1 表示后续增强；P2 表示后续完善或预留能力。后续明确调整覆盖早期优先级：V0.7 将 AI 辅助批改从 V0.6 的 P1 提升为 P0，V0.23 将常见计算、解方程和应用题的 AI 辅助评分纳入首期范围。

第一阶段不开发学生登录、学生在线答题或学生 AI 辅导。学生作为教师管理与分析的数据对象，保留身份标识及未来账号关联能力。生成的练习由教师审核、下载或打印后在线下使用。

AI 能力覆盖 L1 试卷识别与数据处理、L2 掌握度分析与学习诊断、L3 教学建议、L4 练习题及教学材料生成；结果须有解释、证据及人工审核机制，按里程碑交付。

## 2. 用户角色与权限

第一阶段确定四类角色。

| 角色 | 主要职责 | 核心功能 |
|---|---|---|
| 平台超级管理员 | 运营整个 SaaS 平台 | 学校开通、套餐、配额、平台运行状态 |
| 学校管理员 | 管理学校组织与账号 | 学年、班级、教师、学生、权限 |
| 教研负责人／教学主管 | 监督教学质量 | 年级、学科、班级分析，教学干预进展 |
| 学科教师 | 执行日常教学 | 试卷、阅卷、学情诊断、AI 建议、教学事件 |

### 2.1 权限控制要求

采用 RBAC（基于角色的访问控制）与数据范围控制相结合的方式。

**仅有角色权限不足以保证安全。**

例如，两位教师都具有「查看学生成绩」权限，但默认只能访问自己被授权的班级和学生。

因此，服务端必须同时验证：

- 当前用户所属学校；
- 当前用户角色；
- 用户与班级、学科、学生的授权关系；
- 请求操作所涉及的数据范围。

平台超级管理员也不应默认拥有无限制查看学生个人学习记录的权限。

## 3. 多租户 SaaS 架构需求

### 3.1 租户模型

每所学校或教培机构对应一个独立租户。

第一阶段采用共享应用、逻辑隔离的数据架构。

核心业务数据必须包含明确的租户归属，并通过服务端机制执行隔离。

### 3.2 租户生命周期

学校租户需要支持：

| 状态 | 含义 |
|---|---|
| Trial | 试用中 |
| Active | 正常订阅 |
| Expired | 订阅已到期 |
| Suspended | 暂停服务 |
| Closed | 已终止服务 |

具体状态转换规则将在技术设计阶段细化。

### 3.3 订阅与配额

第一阶段支持平台管理员人工开通学校，并配置：

- 试用期；
- 订阅套餐；
- 教师和学生数量配额；
- 文件存储配额；
- AI 使用配额；
- AI 调用量与费用统计。

暂不开发在线支付、自动续费及自助购买。

**验收要求：** 学校 A 的用户即使修改请求参数，也不能读取、修改或下载学校 B 的数据和文件。

### 3.4 商业化与数据保留规则

租户隔离与套餐限制独立设计；租户隔离不随套餐改变。平台管理员初始化学校管理员账号，配置学校可使用的功能和资源额度。

AI 用量统计应覆盖调用量、处理页数、Token 和成本，并可按学校与任务类型汇总。用量统计与配额限制分开管理。

订阅到期可根据合同和配置限制新增考试及 AI 任务；历史成绩与教学记录的保留、导出和删除遵循明确的数据管理政策，不因订阅到期直接删除。具体状态转换及保留政策仍需细化。

## 4. 学校组织管理

### 4.1 核心实体

第一阶段支持以下组织关系：

```text
学校 Tenant
  └── 学年 Academic Year
       └── 学期 Semester
            └── 年级 Grade
                 └── 行政班 Class
                      ├── 学生 Student
                      └── 任课教师 Teacher
```

实际数据模型需要区分组织实体与带有生效时间的关联关系。

例如，学生转班后，历史考试成绩仍应关联其考试发生时所在的班级。

### 4.2 主要功能

支持学校管理员维护教师、学生、班级、任课关系和学年学期信息。

需要保留学生转班、教师任课变化等历史关系。

跨行政班的教学班、复杂教学分组和多校区管理放在后续阶段。

### 4.3 首期组织功能与历史关系

| 功能 | 第一阶段要求 |
|---|---|
| 学年、学期与年级 | 支持学校组织与历史数据管理 |
| 行政班 | 创建、编辑、归档 |
| 教师 | 维护信息、角色、权限及跨班跨学科任课关系 |
| 学生 | 维护信息、学习档案、入班、转班、升班记录 |
| 组织关联 | 记录生效时间及历史版本，供考试与教学事件追溯 |

独立教学班、教研组组织管理、多校区及复杂跨班教学场景为 P1。教研负责人角色与权限属于首期范围，不等于首期实现完整教研组组织管理。

## 5. 数学知识图谱

### 5.1 学段范围

首期覆盖：

**小学三年级至初中三年级的数学知识体系。**

后续扩展其他学科时，不应要求重写整个知识图谱基础服务。

### 5.2 知识图谱分层

采用三层结构：

| 层级 | 说明 |
|---|---|
| 平台标准知识图谱 | 平台统一维护的知识节点及关系 |
| 学校定制知识图谱 | 教材版本、教学进度及学校教学要求 |
| 学生知识掌握状态 | 学生对知识节点的掌握度和相关证据 |

学生掌握状态不属于公共知识图谱内容，必须按租户隔离。

### 5.3 既有项目复用

此前使用 Cursor 和 WorkBuddy 开发的初中数学知识图谱，可以作为知识内容和质量检查结果的参考。

但不能未经验证就直接将原有数据结构作为 SaaS 正式数据库模型。

### 5.4 图谱版本及知识关联

知识图谱应支持多学科、多教材版本、多租户，并记录图谱版本；更新知识节点不能破坏已有学习记录的追溯。

平台标准图谱包含知识节点、关系、教材映射及前置依赖。学校可配置教材版本、教学进度、自定义知识点或标签。题目与知识节点应建立关联，供掌握度分析使用。

复用既有项目时保留经过检查的知识内容、关系和质量报告作为参考，重新设计 SaaS 数据模型；暂不要求直接合并原项目代码。

## 6. 题库管理

题库分为三个层级：

| 层级 | 可见范围 |
|---|---|
| 平台公共题库 | 经授权的学校和教师 |
| 学校私有题库 | 当前学校内的授权用户 |
| 教师个人题库 | 题目创建者及其授权对象 |

题目来源包括人工创建、批量导入、试卷自动提取和 AI 生成。

题目应支持版本、知识点关联、难度、题型、答案和评分规则。

**默认原则：学校上传的试卷和从中提取的题目不自动进入平台公共题库。**

### 6.1 题目来源与审核

试卷自动提取入库、教师手工创建或批量导入、AI 生成题目均属于 P0。AI 生成时可指定知识点、题型和难度；教师审核后保存，正式发布前必须完成审核。

同一道题可关联多个知识点。题目版本管理应避免后续修改影响历史考试。

### 6.2 所有权与共享

教师个人题库默认由教师本人使用，可将题目共享到学校题库。学校可将具有授权的题目提交平台公共题库，由平台审核。

题目所有权、使用授权、共享权限需分开管理，尤其是商业题库。学校试卷及提取题目默认不跨租户共享。

## 7. 试卷与考试管理

### 7.1 数据实体

必须区分：

**试卷 Paper：** 可复用的题目集合。

**试卷版本 Paper Version：** 某次使用的固定题目和顺序。

**标准答案 Answer Key：** 对应试卷版本的参考答案。

**评分规则 Rubric：** 各题及评分点的计分要求。

**考试 Exam：** 某个时间、范围内组织的实际考试活动。

**学生作答 Attempt：** 某位学生参加考试形成的作答记录。

### 7.2 主要业务流程

```text
创建或导入试卷
       ↓
AI 提取题目
       ↓
教师确认题目结构
       ↓
上传标准答案与评分规则
       ↓
创建考试
       ↓
上传学生答卷
       ↓
AI 识别与建议评分
       ↓
教师复核
       ↓
确认并发布成绩
       ↓
更新学情分析
```

已用于正式考试的试卷版本不能被直接覆盖修改。

成绩修订必须保留修改记录。

### 7.3 考试范围与状态

支持教师创建单班考试，以及学校组织多班或年级统一考试。记录参考学生、缺考情况、答卷和成绩状态。

同一试卷可以用于不同班级及考试；固定试卷版本、答案与评分规则保证历史考试不被后续修改影响。

统一考试分析支持班级对比、年级及知识点分析；只有已确认的正式成绩才能进入正式掌握度计算与诊断。

标准答案、评分规则及 AI 提取的题目结构均须教师确认后用于批改。评分规则可包含解题步骤和部分得分要求。

## 8. AI 辅助批改

这是第一阶段最重要的核心能力之一。

### 8.1 首期题型范围

| 题型 | 第一阶段 |
|---|---|
| 单选、多选、判断 | 支持 |
| 常见填空题 | 支持 |
| 计算题 | AI 辅助评分 |
| 解方程题 | AI 辅助评分 |
| 应用题 | AI 辅助评分 |
| 复杂几何证明 | 后续增强 |
| 几何作图 | 后续增强 |

这里的「支持」不意味着每份手写答案都可以完全自动识别。

无法可靠识别或评分的题目必须进入人工复核流程。

### 8.2 上传方式

首期支持浏览器上传 PDF、JPG、PNG 和 ZIP 批量文件。

支持标准化答题卡和已经由教师批改的试卷。

整张复杂手写试卷的识别能力逐步增强。

### 8.3 异步处理

文件上传完成后，由服务器后台执行识别和批改。

即使教师关闭浏览器，后台任务也应继续运行。

任务需要支持进度查询、失败记录和安全重试。

### 8.4 人工复核工作台

同时支持：

- 按学生复核整份答卷；
- 按题目集中复核多名学生的答案。

教师可以查看原始图像、识别文本、标准答案、评分规则、AI 建议分数及评分依据。

教师修改结果后，系统保留原建议和修改记录。

### 8.5 评分发布

**AI 输出的是建议评分，不是未经确认的最终成绩。**

只有经过规定的人工确认流程，成绩才能进入正式学情分析。

### 8.6 数据采集与统一学习数据层

第一阶段优先支持试卷、答题卡、已批改试卷上传，以及 Excel 成绩和逐题得分导入。Excel 亦支持学生信息导入。

标准答案支持 PDF、图片、Word 文件或手动录入；评分规则支持题目分值、参考答案及部分得分规则。Word 支持范围来自 V0.6 的标准答案输入要求，不扩展为所有学生答卷格式。

不同来源应转换为统一学习数据：学生、试卷或作业、题目、学生作答、得分或正误、知识点关联，以及有足够证据时的错误类型。仅有考试总分通常不能支持具体知识点诊断，不得补造逐题证据。

在线答题及第三方系统对接为后续能力，预留统一接入模型与接口。

### 8.7 批量处理与身份匹配

| 功能 | 首期规则 |
|---|---|
| 身份自动匹配 | 根据考号、学号、二维码等关联学生 |
| 身份冲突或无法识别 | 教师人工确认，不直接写入某学生档案 |
| 批量部分成功 | 保留成功结果，单独记录并重试失败部分 |
| 原始文件留存 | 保留试卷、答卷和标准答案供复核 |
| 任务状态 | 展示待处理、处理中、已完成、失败等状态 |

手机拍照上传和扫描设备集成为 P1；先采用 Web 批量上传与后台异步处理。

### 8.8 复核规则与后续增强

复核工作台应标记识别失败、评分冲突和可疑结果；低置信度结果必须人工复核。符合预先定义质量标准的高置信度客观题可批量确认，不能绕过教师确认流程。

保存 AI 原始建议、人工最终确认结果、修改历史和确认时间。支持快捷切换答卷、调整得分和确认，尽量减少教师操作。

智能抽检、多教师协同阅卷及分题分工为 P1。数学题型覆盖与手写识别能力分别评估；无法可靠识别的解题步骤转人工处理。复杂几何证明、几何作图和综合题为后续增强。

## 9. AI 批改质量验收

采用已确认的分层质量基准。

| 指标 | 要求 |
|---|---|
| 答案识别准确率 | 按题型分别评估 |
| 评分一致性 | 与人工参考评分对比 |
| 异常检出率 | 衡量无法可靠处理的答案是否被识别 |
| 高置信度误判率 | 重点控制错误结果被标记为可靠 |
| 教师复核工作量 | 统计复核数量、修改次数及耗时 |
| 批量处理性能 | 统计吞吐量、耗时及失败率 |
| AI 处理成本 | 统计每份答卷和每场考试的费用 |

目前不设定缺乏实测依据的准确率承诺。

M0 进行技术可行性验证，M3 建立测试基准，学校试点期间验证实际效果。

### 9.1 可重复执行的质量基准

测试集包含试卷、标准答案、评分规则、学生答案和人工确认的参考评分。按题型分别评估，不能使用一个总体准确率掩盖题型差异。

模型或评分策略变更后，使用相同基准数据重新测试，并生成质量对比报告，检查质量退化。模型替换必须经过质量验证。

### 9.2 分阶段验收边界

| 阶段 | 验证内容 | 结论边界 |
|---|---|---|
| M0 | 真实试卷、标准答案识别与匹配；模拟答卷流程 | 验证技术路径，不宣称真实学生批改达标 |
| M3 | 人工标注参考集、题型质量与功能流程 | 可完成模拟测试；真实场景质量仍需样本验证 |
| 学校试点 | 经授权、适当脱敏的真实学生答卷 | 评估评分一致性、复核工作量、成本与性能 |

识别准确率、评分一致性与自动处理率分别衡量。正式质量和性能阈值依据测试结果及学校要求确定，当前未确认任何准确率百分比或批量完成时限。

## 10. 学生知识掌握度

首期采用可解释的多因素模型。

综合考虑答题正确性、题目难度、知识点关联权重、时间因素、错误类型、重复证据和前置知识等信息。

每个知识点的评估至少应区分：

**掌握度：** 当前证据支持的学习表现评估。

**可信度：** 现有证据是否足以支持该评估。

当学生只有极少量答题记录时，不能生成看似精确但缺乏依据的结论。

模型版本和历史计算结果应可追踪。

### 10.1 掌握度引擎要求

建立独立的 Knowledge Mastery Engine。第一阶段采用多因素加权模型，预留 IRT、BKT 等知识追踪模型扩展。

掌握度与可信度分别计算；证据不足时显示数据不足，不强行给出精确结论。核心数值来自可验证、可复现的计算机制，不以 AI 自然语言主观判断替代。

支持查看计算依据，保留掌握度变化历史、算法版本及相关证据。

<a id="ch11"></a>

## 11. AI 教学诊断与建议

AI 建议可以由三类方式触发：

| 触发方式 | 示例 |
|---|---|
| 事件触发 | 一次考试成绩确认后 |
| 周期触发 | 定期分析班级知识薄弱点 |
| 教师触发 | 教师主动请求某学生的学习诊断 |

建议必须关联相应学习证据，并提供适用范围、建议行动和必要的解释。

教师可以接受、忽略或执行建议。

系统需要记录建议状态，避免重复推送相同问题。

### 11.1 建议优先级与生命周期

建议按问题严重程度、影响人数与证据可信度排序。相同问题优先更新已有建议，避免重复创建。

教师可指定班级、学生、知识点与时间范围发起诊断，可采纳、修改或忽略建议。系统追踪建议生成、处理、执行与验证过程。

管理层可查看问题与改进进展的汇总；教师始终保有教学决策权。

### 11.2 AI 内容生成

支持 AI 生成练习题及教学材料，由教师审核后使用；生成题目按题库审核和版本规则管理。首期由教师下载或打印后线下安排，不依赖学生在线登录。

<a id="ch12"></a>

## 12. Teaching Event 教学事件

Teaching Event 是连接 AI 诊断与实际教学行为的核心实体。

教师可以手动创建教学事件，也可以从 AI 建议一键创建。

### 12.1 事件内容

包括教学目标、涉及学生或班级、知识点、问题证据、干预措施、执行时间、执行状态和教师反馈。

### 12.2 后续效果验证

系统在出现新的学习数据后，比较干预前后的相关表现，并提示教师查看结果。

但必须注意：

**干预后的成绩提高，不等于可以直接证明成绩提高完全由该干预造成。**

系统应展示变化及证据，而不是作出没有充分依据的因果结论。

### 12.3 首期事件状态与确认

教学事件关联学校、班级、学生、教师和知识点。从 AI 建议创建时预填问题证据、学生、知识点及措施，减少教师操作。

状态包括计划中、进行中、已完成、待验证、已验证。后续考试或练习数据用于展示干预前后得分率、掌握度及可信度变化；教师可以确认验证结果并补充评价。

保留执行、反馈与验证历史。跨教师协作、复杂教学计划、任务分配和教研组统一干预项目为 P1。

## 13. 管理分析与数据中心

学校管理员和教研负责人可在授权范围内查看：

学校 → 年级 → 学科 → 班级 → 学生的分层分析。

包括考试表现、知识薄弱点、学习变化、教学建议处理情况和 Teaching Event 进展。

管理视图应以支持教学改进为目标，而非仅仅生成教师或学生排名。

### 13.1 分层分析与证据下钻

管理工作台与教师工作台分别服务整体教学管理及具体教学任务。支持由学校、年级、学科、班级、学生汇总指标下钻至试题和知识点证据。

查看范围受组织授权与数据权限约束；平台运营权限不默认授予学生个人学习数据的任意访问权。

## 14. 非功能需求

| 领域 | 核心要求 |
|---|---|
| 安全 | 严格租户隔离、服务端权限验证 |
| 隐私 | 对未成年人信息采取适当保护措施 |
| 可用性 | 日常操作不受长时间 AI 任务阻塞 |
| 可追溯 | 保留成绩、AI 建议及人工修订记录 |
| 可恢复 | 数据库备份、恢复验证、故障处理 |
| 可扩展 | AI Worker 可独立扩容 |
| 可维护 | 模块化单体业务后端、独立 AI 服务 |
| 可测试 | 自动化测试与独立 Agent 质量检查 |
| 可观测 | 日志、任务指标、错误告警、成本统计 |

首期容量设计基准为 **500～2,000 名学生、30～150 名教师**，实际试点学校规模仍待确认。

### 14.1 容量与性能设计边界

| 设计项 | 已确认规划 | 状态说明 |
|---|---|---|
| 学生容量基准 | 500 至 2,000 名 | 设计基准，非试点实测人数 |
| 教师规模 | 30 至 150 名 | 设计基准，非已签约用户数 |
| 单次考试规模 | 500 至 2,000 份答卷 | 处理规模规划，非已测吞吐量 |
| 后续扩展目标 | 5,000 名以上学生的学校 | 架构扩展目标，非已验证容量 |

优先保障教师工作台及日常管理响应；AI 批改与大规模分析异步执行，通过队列、并发控制及增加 Worker 扩容。支持多个学校租户，避免某校批量任务长期占用全部处理资源。

服务器配置按试点实际负载确定。处理时延、吞吐量、失败率和费用门槛待 PoC 及真实测试确定。

### 14.2 数据保护与部署区域

首期语言为简体中文，优先中国大陆境内部署、存储和处理学生数据；优先评估符合该部署及处理要求的 AI 服务。

对学生姓名、学号、答卷、成绩及诊断信息实施访问控制、审计和必要的保护。需考虑告知及同意、数据保留和删除等事项；具体合规措施在正式上线前结合实际业务和服务商专项评估。

发送给第三方 AI 的身份信息应最小化，可用匿名答卷编号时不额外发送姓名，并明确服务商处理与存储政策。此处记录产品要求，不构成已经完成的合规评估结论。

## 15. 技术架构基线

此前已经确认的技术选型如下。

| 层级 | 技术 |
|---|---|
| Web | React + TypeScript + Vite + Ant Design |

原有 `index.html` Demo 继续作为产品视觉与交互设计参考。

### 15.1 统一 AI 服务与模型适配

| 能力 | 优先级 | 要求 |
|---|---|---|
| 统一 AI 接口 | P0 | 业务模块通过统一服务调用模型，不直接耦合供应商 API |
| 按任务配置模型 | P0 | 识别、批改、知识关联、教学建议可使用不同模型 |
| 结构化输出 | P0 | 符合数据结构并经过程序校验后进入业务流程 |
| 日志与成本 | P0 | 记录任务、模型、版本、耗时、状态及学校成本 |

| 供应商切换、故障降级、学校 AI 策略 | P1 | 预留并后续完善 |
| 私有化模型部署 | P2 | 后续按学校需求实施 |

数学知识图谱以 PostgreSQL 起步。NestJS 采用模块化单体管理核心业务数据，Python AI 服务与 Worker 独立运行。

### 15.2 代码组织与开发规范

采用 Monorepo，包含 Web、API、AI Service、共享类型、API Client、基础设施与产品、架构、接口、决策、质量报告文档。建立 Cursor Rules 与 AGENTS.md。

数据库变更使用 Migration；前后端按明确接口契约协作。功能和架构变化同步文档，所有阶段包括必要自动化测试及独立检查。

### 15.3 部署与运维

首期采用 Docker 应用部署及云端托管 PostgreSQL、S3 兼容对象存储；Redis 支持托管或独立部署。开发环境通过 Docker Compose 重复搭建。

Web 使用 HTTPS；Development、Staging、Production 环境隔离。建立自动备份、恢复验证、应用与任务日志、错误告警及自动测试、构建和受控部署。

部署记录应用、数据库 Migration 和 AI 服务版本，并支持回退及明确恢复方案。数据库变更不能仅靠应用代码回退恢复。

完整国际化界面、海外环境、Kubernetes 与私有化部署不在首期交付中，保留后续配置和扩展能力。

## 16. M0–M7 开发里程碑

| 里程碑 | 主要交付 | 核心验收 |
|---|---|---|
| **M0** | 项目框架、登录、租户隔离、开发环境、AI PoC | 环境可启动，租户隔离有效，AI 技术路径得到验证 |

| **M3** | 试卷上传、AI 批改、人工复核 | 真实 AI 流程可运行，成绩确认与审计完整 |

| 真实学生答卷 | 尚需协调 | 先用模拟答卷，后续补充授权脱敏样本 |

| 教师批改结果 | 尚需协调 | 建立人工参考评分，再补充真实样本 |
| 异常测试数据 | 可以自行生成 | 模糊扫描、缺页、重复上传、身份失败等 |

“可以获取”是原需求讨论的数据可得性记录，不表示本文件制作时已取得或完成测试。

### 17.2 后续细化范围

实际学校人数、教材版本、模型和云服务商、准确率与性能门槛均需进一步验证。租户状态转换、数据保留政策、权限矩阵、掌握度权重及 AI 任务和成绩状态机由技术设计进一步细化。

尚未确认试点实测结果、完成日期、准确率百分比、自动处理比例、固定处理时限或单份答卷成本。本规格书不将这些内容作为已验证事实。

## 18. V1.0 需求基线结论

目前我们已经明确了产品的核心边界：

**第一阶段要交付的不是一个能够展示 AI 分析结果的 Demo，而是一套能让学校完成真实考试处理、教师复核、学情诊断和教学干预的 SaaS 系统。**

同时，系统必须具备可靠的租户隔离、成绩审计、AI 成本控制及可持续扩展能力。

技术架构确定后，再形成 M0 Cursor Development Prompt、QA Prompt 和 Architecture Review Prompt。本文件作为需求基线初稿，不替代上述技术设计和阶段验收报告。
