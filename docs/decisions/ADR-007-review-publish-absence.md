# ADR-007 复核、确认发布语义、缺考与部分发布

- **状态：** Proposed（2026-10-12 修订，未签署）。v3 分析消费 `ScorePointerAdvanced`。`attribution_corrected_away` 仍待负责人在选项甲/乙中选择。
- **2026-10-13 M0 范围：** 项目负责人在对话中批准决议清单第 2 节对本 ADR「建议批准」列的条款，并接受第 3 节保守恢复政策。见 `g0-decision-record-20261013.md`。同表「仍保留待定」列和未列入的未来细节仍是 Proposed。本 ADR 整体不是 Accepted。
- **日期：** 2026-10-11；修订 2026-10-12
- **2026-10-12：** 首次发布按学生的 `basis_mode` 验收。`total_only` 可以成为正式总分，不制造题级证据，也不要求逐题 review。缺考 total 为 NULL。空白记零是 numeric 0 加上原 blank 行。发布后换绑尚未决议：选项甲才使用 `attribution_corrected_away`；选项乙保持命令拒绝。不新增部分首发或撤回。
- **决策责任：** 项目负责人
- **关联：** R14、R15、R24；F19、F20、F23
- **证据：** 已确认“授权教师确认后正式成绩才进入分析”，以及合格客观题可以批量确认。架构初稿把 Confirmed 与 Published 分成两个数据库状态，并说明产品上可以是一个按钮。用户没有单独选择其中一种。

## 问题

若 Confirmed 已经触发分析，而 Published 才被另一些模块当成门槛，未发布成绩会进入学情。修订若停在 Reconfirmed，当前成绩会悬空。批量按钮若按筛选条件执行，会确认教师没看见的新结果。

## 方案

### A. 推荐：一次产品操作，一个发布事务

- 首次按钮对应 `PublishScoreVersion`。
- 不存在会触发分析的静息状态 Confirmed。
- 分析只消费 `ScorePointerAdvanced`，且该版本仍是当前指针。旧事件名不生产。
- 修订用 `RepublishRevision` 一次完成 vNext 的批准与指针切换。v1 在此之前保持有效。
- 批量确认是显式 ID + 版本 + 策略快照，整组原子提交。
- 缺考由教师 `RecordAbsence` 显式批准，不写 0 分，不产生知识点证据。
- 首次发布必须覆盖整份名单。
- 不提供成绩撤回，也不提供“首次只发布一部分学生”。二者产品基线未确认。

### B. 保留 Confirmed 与 Published 两段，但只有 Published 事件触发分析

数据库能表达“教师已看过但学校尚未公布”。当前没有产品句子要求这个停顿。若采用 B，必须写明谁能看见 Confirmed，并且任何模块都不得订阅 Confirmed 做掌握度。

### C. 允许队列部分成功直接变成部分正式成绩

把处理失败和成绩发布混在一起。不推荐。

## 代价

方案 A 下，教师不能先内部确认再择日公布。若试点学校需要这个停顿，应接受 B 而不是由开发时自行加状态。

未校准前全部人工，批量确认按钮会很少可用。这是 R24 的后果。

## 兼容与回退

事件名不用 `ExamScoresConfirmed`。若决议改为 B，增加事件而不是复用 Published 表示两种含义。

## 故障模型

少一题、未匹配、低置信未审、复核过期、权限在发布前被撤销、批量列表在提交前变了、修订被拒绝、两人同时再发布。

## 验收

非法边无成功 Outbox。修订失败时旧指针仍在。再发布后只有一个当前版本。缺考与 0 分可区分。测试未运行。
