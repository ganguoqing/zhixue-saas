# ADR-012 额度预留、未知费用与租户在途策略

- **状态：** Proposed（2026-10-12 修订，未签署）
- **日期：** 2026-10-11；修订 2026-10-12
- **2026-10-12 撤回：** 把每租户 running cap 称为公平调度；在接纳时才第一次写入 invocation。现行：轮转 admission、按 stage 预留、调用前 intent、unknown 标记不进官方合计。测试值与生产空值分开，见事务文档 v2 第 7 节。本 ADR 整包仍待接受，不要只接受 v1 原文。
- **决策责任：** 项目负责人
- **关联：** R25、R26、R17；F14、F17
- **证据：** 已确认配额、成本可追踪、到期不删除数据、学校之间不应长期占满处理资源。在途任务在到期或暂停时是完成还是取消，没有单独确认。

## 问题

并发任务会超卖配额。业务去重会掩盖多次付费。超时可能已经在供应商侧计费。开源 BullMQ 的 Python 侧不能假设具备 Pro 的分组公平。

## 方案

### A. 推荐：调用前意图、差额账本、租户轮转 admission

- 创建 job 的同一事务预留额度。
- 每次真实调用先有 intent。未知用 `unknown_marker`（金额 NULL，不进合计）。确认只追加 `confirm_delta`。禁止把 unknown 写成 0。
- 调用前先提交 invocation intent。unknown 标记不进入官方合计；确认用新的 `confirm_delta` 行。
- 套餐限制不代替数据权限。
- 预留按 stage。`expired` 只允许已经 admission 的当前 stage 跑完，不开始下一 stage。`suspended` 取消未完成的当前 stage。关闭不立即删数据。详见事务文档 v2 第 7 节。
- 公平挑选是租户轮转加 admission。并发上限只限制选中后能否占用，本身不是公平调度。不依赖 BullMQ Pro。
- 缓存、锁、去重键和周期任务的名字包含环境与租户。

### B. 只在月底统计，不预留

不能阻止并发超限。不推荐作为 P0 协议。

### C. 到期立即删除或立即杀掉并丢弃账

与 R25 冲突。不推荐。

## 代价

预留按 stage，避免一次预留挡住后续阶段的到期政策。轮转与上限的测试值见事务文档，生产数字仍不填写。

## 兼容与回退

状态矩阵若被改成“暂停也允许在途完成”，只改变领取条件，不改变账本结构。

## 故障模型

并发超卖、一次任务两次付费只记一次、unknown 被记零、A 校队列堵住 B 校、到期租户继续调用模型、同名缓存键串租户。

## 验收

并发配额测试不超发。两次真实调用都有账。unknown 不会显示为 0。积压场景下另一租户仍能领到已配置的并发位。测试未运行。
